## Decisions needed from the human

The lead's own calls inside the spec are recorded in the journals: SAN-001.D1–D3, D8–D10, FOP-001.D1, DB-002.D1–D2, ING-002.D2, MOD-001.D1–D3 and TST-005.D3. These are the ones that are yours:

1. **ING-001.D2 — Does the source-path exception (DOC-004.D3) last past M2?** It lets the container path (`/source/...`) sit in `files.source_path`, `files.duplicate_paths` and the local reports.
   - **A (recommended): permanent for the ledger and the local reports, and never passed further.**
     - The ledger can't drop it: M7's copy, `purge-sources`, `delete` and `watch` all need the path to find the original.
     - From M2 on, add two limits: no model ever receives the path or the raw name, only `files.original_sanitized` (P-2); and the M4 API and UI show the sanitized name and hashes, never `source_path`.
     - The dry-run CSV keeps `source_path`, beside a new `sanitized_name`, because you read it locally to check the sort.
   - **B: permanent for the ledger, ended for the reports.** From M2 the CSV carries only `sanitized_name` and the hash. Safer if a report is ever copied off the box, but harder to trace a row back to its file by hand.
   - **C: ended everywhere at M2.** Not workable: the ledger is the only way M7 finds the original.

   Either A or B needs a small rule-change PR from your session (CLAUDE.md's exception, DOC-004.D3) to name the end state. CLI-003.1 waits for the answer.
2. **Backlog scope.**
   - **CFG-002, TST-003, TST-004: in M2 (recommended).** CFG-002 keeps the database password out of the committed `config.yaml` (CFG-001.D2). TST-003 is the helper SAN-001.4 and CLI-003.1 build on. TST-004 guards the default tiers before gate 2, the first new reader of the real fixtures.
   - **RUN-004 (lockfile): out of the plan, recommended after M3.** It is a Dockerfile and Makefile change, which no desk role owns, so it is a human-side PR (RUN-002.D16). M3 adds the SigLIP and NSFW stack, so a lock taken after M3 doesn't churn at once. Say if you'd rather do it now.
   - **RUN-010 (guard residuals, CLAUDE.md wording, `create_host_path`): out of the plan.** It is human-side. Item 3 matters for gate 2: with `create_host_path: true`, a checkout with no fixtures reports "empty", not "missing". Doing it before TST-005.2 lands would help.
3. **SAN-001.D4 — The ICC colour profile: keep or strip?** `exif.keep` names only `Orientation` and `DateTimeOriginal`, so a strict reading strips the ICC profile too. Without it, wide-gamut images (many phone photos) render with shifted colours. A profile can carry a device or vendor description, but rarely anything personal.
   - **Recommended:** keep the ICC profile and count it as a file-structure tag, not metadata.
   - **Alternative:** strip it; to keep it then, the profile has to be added to `exif.keep` by hand.
4. **SAN-001.D5 — `sanitize_log.before_hash`: plain SHA-256, or HMAC-SHA256 with a local key?**
   - A plain hash of a short value, such as a first name, can be reversed by guessing it from a list. R-SAN-6 means "never stored in plain text"; a plain hash meets the letter of that, but not the intent.
   - **Recommended: HMAC** with a key in `.env` (`SANITIZE_LOG_KEY`, generated by `make init`). That is a small Makefile and `.env.example` change, human-side, needed before SAN-001.1 merges. The log stays auditable on the box: you can check whether a value was redacted by hashing it with the key.
   - **Alternative:** plain SHA-256, as written, with no other change.
5. **SAN-001.D6 — Keep the `claude` backend and OCR out of M2?** **Recommended: yes.** §11's M2 scope names only the local LLM. OCR needs the VLM (M5 at the earliest). Until they land, `sanitizer.backend: claude` and `sanitizer.ocr: true` fail fast with a message naming the key.
6. **SAN-001.D7 — Working copies persist in `results_root/.work/` during dry runs.** P-2 means classify (M3) and caption (M5) read only the sanitized copy, so the copy has to persist from sanitize until M7 files it.
   - **Recommended: confirm.** Note that `.work/` then needs about as much space as the source folder, on the results drive.
   - **Also note, for M7:** R-FOP-3 ("`.work/` is cleaned on start, except `thumbs/`") would delete the copies a resumed run needs. M7's plan should narrow it to temp files and the copies of `filed` or `error` rows. No change is needed now.
7. **ING-002.D1 — The thumbnail name: `<short_hash>.webp` (R-ING-5) or `<source_hash>.webp`?**
   - Eight hex characters are 32 bits, so two files share a `short_hash` with odds of about N²/2³³. That is about 1% at 10,000 files: a real chance on a big folder, and either a lost thumbnail or a wrong one.
   - **Recommended: `<source_hash>.webp`.** It needs a one-line DESIGN.md change to R-ING-5, from your session.
   - **Alternative:** keep `<short_hash>` and accept the collision risk.
8. **TST-005.D1 — Who commits a task's recordings?** `tests/recordings/` is QA's shared infrastructure, but MOD-001.2's `gpu` run is what produces the recordings SAN-001.3 and SAN-001.4 replay.
   - **Recommended:** like DOC-004.D1, the worker commits its own task's recordings under `tests/recordings/<package>/`, made from synthetic strings only, and QA owns the format and the replay fixture. This needs a CLAUDE.md line from your session.
   - **Alternative:** QA records them in an extra task after MOD-001.2, which adds a step to the critical path.
9. **TST-005.D2 — Where gate 2's seeded values come from.**
   - **Recommended:** the gate builds 50 names with a pinned seed from three sources. (a) The literal values in your local `sanitize.yaml`, read inside the container and never printed, so the gate measures your real rules. (b) Synthetic emails and phone numbers. (c) A committed list of fictional person, organisation and place names, for the entity rule.
   - **Alternative:** synthetic values only, plus a committed `sanitize.gate.yaml`. It is fully reproducible in public, but it doesn't test your rules.
